## Objective

1. Build a provider VPC with two subnets across two AZs and an internal NLB
2. Publish the NLB as an Endpoint Service (PrivateLink provider side)
3. Consume the Endpoint Service via an Interface VPC Endpoint (consumer side)
4. Observe ENI creation and DNS entries generated by the endpoint
5. Document the PrivateLink architecture and cost model

## Concept: What PrivateLink Is

PrivateLink lets a service in one VPC be consumed by principals in another VPC (or another AWS account, or on-premises) without VPC peering, transit gateway, or public internet exposure. Traffic stays on the AWS network and never leaves it.

The mechanism has two sides:

### Provider side

1. A Network Load Balancer (NLB) fronts the service. Must be `internal` (no public IPs).
2. An Endpoint Service wraps the NLB, giving it a service name.
3. Optional: acceptance required, allowed principals, connection notifications.

### Consumer side

1. An Interface VPC Endpoint points at the Endpoint Service.
2. AWS creates ENIs in the consumer's subnets - one per AZ.
3. The endpoint gets DNS names that resolve to the ENI private IPs.
4. The consumer's workloads connect to the DNS name, which resolves to the ENI, which forwards to the NLB, which forwards to the service.

No peering, no route table entries, no CIDR considerations. The consumer's VPC sees only private IP addresses inside its own CIDR.

## Setup Steps

### 1. Provider subnets

Two subnets in different AZs are required because the NLB must be in at least two AZs for high availability.

aws ec2 create-subnet --vpc-id vpc-0b00f49eaaa30977c --cidr-block 172.31.100.0/24 --availability-zone eu-north-1a --tag-specifications "ResourceType=subnet,Tags=[{Key=Name,Value=lab24-provider-a}]"

aws ec2 create-subnet --vpc-id vpc-0b00f49eaaa30977c --cidr-block 172.31.101.0/24 --availability-zone eu-north-1b --tag-specifications "ResourceType=subnet,Tags=[{Key=Name,Value=lab24-provider-b}]"

### 2. Security groups

Target security group (inbound 80 from VPC):

aws ec2 create-security-group --group-name lab24-target-sg --description "PrivateLink lab targets" --vpc-id vpc-0b00f49eaaa30977c
aws ec2 authorize-security-group-ingress --group-id sg-0b885e2a929e094af --protocol tcp --port 80 --cidr 172.31.0.0/16

Endpoint security group (inbound 80 from VPC):

aws ec2 create-security-group --group-name lab24-endpoint-sg --description "PrivateLink endpoint ENI access" --vpc-id vpc-0b00f49eaaa30977c
aws ec2 authorize-security-group-ingress --group-id sg-05cbaea31840ae150 --protocol tcp --port 80 --cidr 172.31.0.0/16

### 3. Network Load Balancer

aws elbv2 create-load-balancer --name lab24-nlb --type network --scheme internal --subnets subnet-0e7756eec4fa51703 subnet-0203d2efaf9b0ad8a

Important: the scheme must be internal. PrivateLink cannot front a public NLB.

### 4. Target group

aws elbv2 create-target-group --name lab24-tg --protocol TCP --port 80 --vpc-id vpc-0b00f49eaaa30977c --target-type instance --health-check-protocol HTTP --health-check-path /

### 5. Listener

aws elbv2 create-listener --load-balancer-arn arn:aws:elasticloadbalancing:eu-north-1:803964124082:loadbalancer/net/lab24-nlb/36d1ec0f705d12dd --protocol TCP --port 80 --default-actions Type=forward,TargetGroupArn=arn:aws:elasticloadbalancing:eu-north-1:803964124082:targetgroup/lab24-tg/038e7366fcfc4ff8

### 6. Endpoint Service (provider side of PrivateLink)

aws ec2 create-vpc-endpoint-service-configuration --network-load-balancer-arns arn:aws:elasticloadbalancing:eu-north-1:803964124082:loadbalancer/net/lab24-nlb/36d1ec0f705d12dd --no-acceptance-required

Returned:

- ServiceId: vpce-svc-03a3f93be419e45ed
- ServiceName: com.amazonaws.vpce.eu-north-1.vpce-svc-03a3f93be419e45ed
- ServiceState: Available
- AvailabilityZones: eu-north-1a, eu-north-1b

In production, use --acceptance-required so the provider manually approves each consumer connection. Without it, any principal that knows the service name can connect.

### 7. Interface VPC Endpoint (consumer side of PrivateLink)

aws ec2 create-vpc-endpoint --vpc-id vpc-0b00f49eaaa30977c --service-name com.amazonaws.vpce.eu-north-1.vpce-svc-03a3f93be419e45ed --vpc-endpoint-type Interface --subnet-ids subnet-0e7756eec4fa51703 subnet-0203d2efaf9b0ad8a --security-group-ids sg-05cbaea31840ae150

- VpcEndpointId: vpce-09ccecac6c1065fa0
- State: pending then available
- NetworkInterfaceIds: eni-0ed27f0f154b3adff, eni-044c3060d90886dd5
- DnsEntries: three DNS names (regional + per-AZ)

## Key Observations

### 1. The Interface Endpoint creates ENIs, one per AZ

NetworkInterfaceIds shows two ENIs. Each has a private IP in its subnet's CIDR range. This is the entire reason PrivateLink "just works" from the consumer's perspective: the endpoint is a set of private IPs inside the consumer's own VPC.

Compare with the Gateway Endpoint from Lab 2.3 (S3/DynamoDB), which has NetworkInterfaceIds: [] and works via a route table entry instead.

### 2. The Endpoint Service is a first-class AWS resource

Once created, the service is visible in the account as com.amazonaws.vpce.eu-north-1.vpce-svc-03a3f93be419e45ed. Other AWS accounts can call create-vpc-endpoint referencing this service name, and (with acceptance required) the provider approves each.

### 3. DNS entries have both regional and per-AZ names

The regional DNS name (vpce-...-l9nz1q1t.vpce-svc-...amazonaws.com) resolves to all endpoint ENIs. Each per-AZ DNS name (vpce-...-eu-north-1a.vpce-svc-...) resolves only to the ENI in that AZ. Applications in a specific AZ should use the per-AZ name to avoid cross-AZ data charges.

### 4. Targets were unhealthy in this lab

The two EC2 targets registered to the target group were in `Target.FailedHealthChecks` state at the end of the lab. This is not a PrivateLink issue; it is an application issue. The user-data script intended to install and start Apache did not complete successfully before the health check deadline, and the targets never became healthy.

The PrivateLink architecture itself was fully in place and marked Available by the AWS APIs. The fact that a target app was not responding does not change the endpoint's state; the endpoint simply forwards traffic to the NLB, which forwards to whatever targets are healthy.

## PrivateLink vs Peering vs Transit Gateway

| Aspect | VPC Peering | Transit Gateway | PrivateLink |
|---|---|---|---|
| Direction | Bidirectional | Bidirectional | Unidirectional (consumer -> provider) |
| CIDR overlap allowed | No | No | Yes (isolated by design) |
| Access scope | Full VPC | Full VPC | Only the specific service |
| Cost model | Data transfer | Attachment + data | Endpoint hourly + data |
| Route tables | Manual | Manual | Not applicable |
| Cross-account | Yes | Yes | Yes |
| Internet exposure | None | None | None |
| Use case | Connect two VPCs | Connect many VPCs | Expose one service |

PrivateLink is the only option that allows the consumer and provider to have overlapping CIDRs, because the endpoint presents itself as a private IP in the consumer's own CIDR.

## Lessons / Gotchas

1. NLB must be internal. PrivateLink will reject a scheme: internet-facing NLB.

2. NLB must span at least two AZs. This is for high availability of the endpoint service itself.

3. Acceptance-required is a security control, not a formality. Without it, any principal who knows the service name can connect. Enable it in production.

4. Interface Endpoint creates ENIs. These consume IPs in the consumer's subnets. In tight subnets, this matters.

5. DNS entries include per-AZ names. Using the per-AZ name prevents cross-AZ data transfer charges in high-throughput applications.

6. PrivateLink is unidirectional. The provider does not initiate connections to the consumer. If bidirectional is needed, both sides must publish endpoint services.

7. Overlapping CIDRs are allowed, unlike in peering or Transit Gateway. This is what makes PrivateLink attractive for SaaS and multi-tenant scenarios.

8. Gateway Endpoints (S3/DynamoDB) and Interface Endpoints (PrivateLink) are completely different mechanisms. Do not confuse them just because they share the word "endpoint."

## Real-World Application

PrivateLink is the standard pattern for exposing a service to external consumers without exposing the network:

- SaaS platforms. A SaaS vendor publishes an Endpoint Service; each customer creates an Interface Endpoint in their own VPC. No peering, no CIDR negotiation, no public exposure. This is how Datadog, Snowflake, MongoDB Atlas, and many others deliver private connectivity.

- Multi-account internal services. A shared services account hosts a central API or database and publishes it via PrivateLink. Every application account creates an Interface Endpoint. No Transit Gateway needed for one-off services.

- Compliance boundaries. When regulations prohibit data crossing the public internet, PrivateLink keeps traffic on the AWS backbone without the complexity of peering or TGW.

- Overlapping CIDR scenarios. Two VPCs with 10.0.0.0/16 cannot be peered but can exchange traffic through PrivateLink. This is the killer feature for acquisitions and multi-tenant architectures.

- On-premises access. Combined with Direct Connect, PrivateLink lets on-premises workloads reach AWS services and custom endpoint services without public exposure.

The cost model (endpoint hourly + per-GB processed) is often cheaper than the equivalent Transit Gateway setup when only one service needs to be shared, and it is dramatically simpler to operate.
